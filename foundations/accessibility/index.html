Foundations / Accessibility

Accessibility

The system aims at WCAG 2.2, level AA, for everything it ships: tokens, components and patterns. What it can guarantee is built in and tested on every build; what only an app can know is written down as rules.

Who does what

What the system guarantees and what each app provides
The systemContrast of every color pair, focus rings, target sizes, keyboard behavior, roles and states of every component, reduced motion.
The appPage titles and headings, the language of the page, the names it gives to components (labels, button text, chart labels), error messages that say how to fix the error, and the order of content.

Contrast

Every text level meant to be read, placeholders included, reaches 4.5:1 on every surface that carries text, in both themes (WCAG 1.4.3). Control boundaries, the focus ring and marks such as checkboxes and chart alerts reach 3:1 (1.4.11). Disabled text is exempt from both; the system still keeps it at 3:1 so it can be read.

The 125 pairs below are a contract in the tokens package, lib/accessibility.ts. The token tests measure each one in both themes on every build, and a change that breaks one fails the build. Each row shows the lowest ratio across its backgrounds, measured now. Every text level on every surface is in the matrix of Color.

Focus

  • Every control shows a ring when it is reached from the keyboard (2.4.7): focus.width 2 px, at focus.offset 2 px, in color.focus, which keeps 3:1 against every surface it can sit on. A ring is never removed without another visible indicator in its place.
  • Pointer clicks draw no ring; :focus-visible decides, as the browser does for its own controls.
  • Nothing covers what has focus (2.4.11). On phones and tablets the top bar is sticky, so the page keeps room for it above anything scrolled into view; menus and tooltips open beside their trigger, never over it.
  • A modal dialog moves focus in and returns it to what opened it; nothing else moves focus on its own.

Target size

  • WCAG 2.2 asks for targets of at least 24 × 24 px (2.5.8). Controls are 28 or 36 px tall, and spaced so that neighbors never overlap.
  • On touch screens every control’s hit area grows to 48 × 48 px, layout.touch-target, without changing how it looks. Labels of checkboxes and switches are part of the target.

Motion

  • Under prefers-reduced-motion, every component stops moving things across the screen: menus, dialogs, sheets and toasts appear in place, and shapes change without traveling. Short fades and color changes remain, so state changes are still visible.
  • Nothing animates on load, nothing flashes, and nothing moves on its own for more than a moment.

Keyboard

  • Everything that works with a pointer works with a keyboard (2.1.1), in the order the page is read.
  • Tab moves between controls; arrow keys move inside a group of options, a menu or a chart, as the platform does. Each component page lists its keys under Accessibility.
  • Only a modal dialog keeps focus inside it, by design, and Escape always leaves it (2.1.2).

Screen readers

  • Native first. Buttons, checkboxes, switches, radios, fields and dialogs are the browser’s own elements, so their roles and states are right in every screen reader. Base UI supplies the rest (menus, tooltips, toasts) following the WAI-ARIA patterns.
  • Every control has a name. Icon buttons require one; icons are hidden; repeated buttons say what they act on.
  • Never color alone (1.4.1). States are written; legends name every color; charts list their values in words.
  • Changes are announced. Toasts arrive in a polite live region, and a card announces what its step buttons change: the day, the due date, the month.
  • Regions. Each card of the overview is a region named by its title, so the overview can be read card by card.

Reflow and text

  • Pages reflow down to 320 px without scrolling sideways (1.4.10). Long code and wide tables scroll inside their own block, which can be focused and scrolled from the keyboard.
  • Text sizes are in the type roles and scale with the browser’s text size (1.4.4); nothing is set to stop zoom.
  • Cards in the overview grid have one of four heights. With very large text or extra text spacing (1.4.12) nothing is cut: content that no longer fits scrolls inside the card, between its header and footer, and can be scrolled from the keyboard.

How it is checked

  • On every build, automatically: the 125 contrast pairs in both themes; every component rendered and checked with axe in its tests.
  • Before every release, by hand and with scripts: every page of this site at 360, 390, 430, 834, 1024 and 1440 px, light and dark, with every code block open, checked for anything that scrolls the page sideways; a keyboard pass through every component; VoiceOver on iOS and macOS through every component; text at 200%.

Known limits

  • The Sonar-DB dashboard is audited on its own, once it is built on these tokens and components; this site covers the system, the patterns and their live examples.
